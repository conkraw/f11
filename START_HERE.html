PICU HANDOFF / SMARTPHRASE FOUNDATION / VERSION 1

Start with Diagnoses.

A fresh web-based Streamlit app. Select a room, paste your separated SmartPhrase, read the Diagnoses block, edit the handoff, and save it to an encrypted private GitHub archive.

Use synthetic information until your institution approves both the app host and the storage service, with required agreements and access controls. A password, private repository, encryption, or omission of names/MRNs does not establish HIPAA compliance. The host receives the pasted text in plaintext before encrypting saved handoffs.

1. What this version does

The app recognizes all ten divider types. Only Diagnoses is imported automatically. The other sections are not clinically interpreted, summarized, or silently added to the handoff. You can edit every system field manually.

No OCR is needed because Epic already provides text. There is no PDF upload, local Windows installation, Tesseract setup, or PDF password in this version. The only app password is the sign-in password. Admin uses that same session.

2. Put the code in a new repository

Extract the ZIP and upload the contents of PICU_Handoff_SmartPhrase_Base to a new private CODE repository. Do not mix this with previous handoff versions.

Keep app.py, parser.py, models.py, security.py, github_store.py, exports.py, requirements.txt, examples/, and .streamlit/config.toml together. The other supplied files provide setup instructions and tests.

Never upload a generated .streamlit/secrets.toml, clinical source text, patient PDFs, or downloaded clinical handoffs. The supplied secrets.example.toml contains placeholders only.

3. Create the private data repository

Create a second private DATA repository and initialize it with a README on the main branch. A separate repository keeps patient-data saves from changing the application's source repository.

Create a fine-grained GitHub token limited to this DATA repository with Contents read/write access. Organization approval may be needed. The app checks repository privacy and the branch before reading or writing.

The app writes one file, encrypted-data/handoff-v1.enc. Its contents, including rooms and Admin settings, are encrypted. Filenames and commit messages do not contain room labels or handoff text.

4. Generate the private settings once

You can use your existing Python or Anaconda installation for this small helper. No new standalone Python is needed on your desktop.

In a terminal inside the extracted folder, run:

python create_secrets.py

Or open Generate_Secrets.ipynb in your existing JupyterLab and run its one code cell. The notebook is only a settings generator, not the app server.

Choose an app password of at least 12 characters, enter the DATA repository as owner/repository, and enter its token. The script creates .streamlit/secrets.toml locally without printing the secret values. Open that file locally and copy its contents into the hosting provider's private Secrets settings.

Leaving the repository blank creates a session-only test configuration. To test durable saves, configure the repository/token and set github_enabled = true in deployment Secrets.

Back up the encryption key in an approved password manager. Resetting a forgotten app password means changing its hash while preserving the encryption key. Losing the encryption key prevents recovery of existing saved data.

5. Deploy the web app

Use app.py as the entry point and Python 3.11 or newer on the host. The host installs requirements.txt. Add the private settings in its Secrets interface and restart the deployment.

Streamlit Community Cloud may be used for a synthetic-data prototype. This package does not establish that Streamlit Community Cloud or a particular GitHub product is approved to receive clinical data. Use only an institution-approved clinical deployment and storage arrangement for patient information.

Keep clinical_use_approved = false during testing. Setting it to true only changes a warning label. It does not create agreements, de-identify content, or validate compliance. Clinical deployment needs institutional identity/access controls, HTTPS, audit/retention arrangements, and appropriate protections beyond this shared-password prototype.

6. Test the first section

  1. Sign in with the app password.
  2. Choose a room and click Open room.
  3. Click Load synthetic example, then Read Diagnoses.
  4. Check the extracted diagnoses and destination, then click Apply diagnoses to handoff.
  5. Use Edit handoff to revise any system. Confirm that you checked the room and text, then save.
  6. Sign out, sign in again, and reopen the room to verify GitHub persistence. In session-only mode, signing out intentionally removes all work.

Admin lets you change the default diagnosis destination and room list. Default rooms are P4102 through P4116 in even increments, followed by 4201, 4203, 4209, and 4211 through 4223 in odd increments. Other room accepts an additional room label.

Use Start blank for new patient whenever a room changes occupants. It clears the draft and generates a new reference. Saving explicitly replaces that room's current saved sheet. A room is not a substitute for patient identification in Epic.

Your example's closing VITALS divider began with c before the e characters. Replace that line with e characters only. The app warns instead of silently guessing. The supplied SMARTPHRASE_TEMPLATE.txt uses consistent dividers. Replace its placeholder instructions with your existing Epic SmartLinks.

What is and is not saved

The archive contains only the editable handoff fields, room references, timestamps, and Admin settings. It does not contain the full pasted SmartPhrase or raw unimplemented sections. Pasted text is still processed on the host and can remain in session memory. Applying diagnoses clears the paste field, not the operating system's memory.

Downloads are unencrypted HTML/text files. Open the HTML in a browser and use Print to print or save as PDF. Earlier encrypted saves remain in Git history. Removing or replacing a current handoff is not a secure purge of that history.

Concurrent GitHub changes are rejected instead of silently overwritten. Reload the archive, compare the saved sheet with the draft, load the current saved version, and reapply any edits. This prototype is not a multi-clinician transactional chart system.
